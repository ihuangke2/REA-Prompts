# REA 调查提示词（REAP）—— 使用你的编码助手进行逆向工程

这是一个精选的提示词集合，适用于 [REA (Reverse Engineer Anything)](https://rea.tools/)——这个工具集可以让你的 AI 编码代理深入研究软件是如何工作的，覆盖范围从原生二进制程序、固件，到桌面应用和更复杂的系统组件。

这些提示词都可以直接复制粘贴到你的 AI 助手中。将 `<angle brackets>` 中的内容替换成你的目标，并让每个请求聚焦于一个具体功能：更窄的范围通常能带来更可靠、且更有证据支撑的答案。

## 这套提示词适合什么场景？

- 追踪一个功能从界面、入口点一路执行到最终副作用；
- 分析二进制程序、库、驱动和固件的结构和行为；
- 还原协议、文件格式、状态机和内核/系统调用逻辑；
- 对已有实现做克隆、重建、对比和安全研究；
- 在受授权范围内探索漏洞、加固点、兼容性和行为差异。

如果你在做逆向工程、软件分析、行为还原、漏洞审计或功能复现，这些提示词都能作为良好的起点。

## 2. 功能追踪（任意程序）

### 解释一个功能

```text

识别入口点、涉及的函数、数据流、依赖项和可观察效果。
```

```text
使用 REA 分析 <binary>。选择处理 <operation> 的函数，并输出：
反编译后的伪代码、它的调用者和被调用者、它读取或写入的数据结构，以及它触碰到的每个字符串/全局变量。为每个发现标注证明其存在的地址范围。
```

### 导入、字符串与分流地图

```text
使用 REA 分析 <binary>。生成一个分流地图：文件格式与架构、段布局、链接库及其按能力分组的导入（网络、文件系统、加密、进程/线程、注册表/IPC）、带地址的关键字符串，以及 <FEATURE> 的主要候选入口点。标出任何打包、混淆或控制流扁平化的迹象。
```

### 文件格式逆向工程

```text
使用 REA 分析 <program>，弄清它如何读取和写出 <file type>。

```

### 协议 / 序列化提取

```text
使用 REA 对 <binary> 进行分析，恢复 <feature> 的网络或 IPC 流量所使用的传输格式。展示 marshal/unmarshal 函数及地址，列出每个字段（大小、字节序、编码），并生成一个 Python struct/proto 定义，以及一个由代码常量构建的示例消息。
```

## 4. 软件与功能克隆

> 清洁室方法：提取行为，而不是复制代码。切勿复制专有源代码、资源、品牌或许可机制。

### 全应用克隆（行为级）

```text
使用 REA 作为黑盒研究 <application>，以进行清洁室克隆。

生成 CLONE_SPEC.md，涵盖：每个用户可见功能、界面和状态机；输入、输出和边界情况；它使用的文件格式和网络协议；设置和持久化布局；错误行为。

对每一项要求，给出证据（函数、地址、字符串、抓取到的请求）。将任何未确认的项标记为 UNKNOWN。不要复制代码或资源——我将只依据规范来实现它。
```

### 将一个功能克隆到我自己的应用中

```text
使用 REA 恢复 <application> 中 <FEATURE> 的精确行为：触发条件、输入、处理步骤、输出、副作用和失败模式。

随后在 <MY LANGUAGE/PROJECT> 中从头实现 <FEATURE>，并使它与恢复出的规则一致，同时使用从恢复规则衍生出的测试进行验证。列出我实现与原版之间仍存在的每个可观察差异。
```

### 评估克隆版本与原版的一致性

```text
比较 <MY IMPLEMENTATION> 与 <ORIGINAL APPLICATION> 的观测行为。

如果可用，使用 verify_reconstruction。检查结果、错误、限制和状态转换。

展示通过的案例、分歧以及尚未测试的行为。不要仅因为几条示例通过就认为等价性已证明。
```

### 仅复制 UI/UX 行为，不复制资源

```text
使用 REA 分析 <application>，记录其交互模型：布局逻辑、键盘快捷键、命令分发、撤销/重做语义和剪贴板格式。然后在 <my framework> 中重建相同的行为，仅使用我自己的视觉资源，并与文档化语义一致。说明每项规则对应的原始函数证据。
```

## 6. 将游戏移植到 WASM

### 将原生游戏移植到浏览器

```text
使用 REA 分析 <game executable/source>，将其作为 WASM 移植目标。

构造地图：主循环和帧节奏、渲染后端（OpenGL/DirectX/SDL/Vulkan 调用）、文件系统和保存路径、线程模型、音频输出、输入处理，以及任何平台特定 API 或内联汇编。

按“可直接移植 / 需要 shim / 必须重写”对每一项分类，并附上证明这些结论的函数和调用点。
```

### 制作移植计划

```text
根据 REA 对 <game> 的发现，输出一个 WASM 移植计划：
- 工具链选择（Emscripten 或手动重编译）及所需 shim（GL→WebGL、SDL→SDL2-compat、pthreads→SharedArrayBuffer/threads）；
- 需要编译的最小源代码模块集合；
- 保存数据如何迁移到 IndexedDB，资源如何获取/流式传输；
- 在原生代码中发现的性能风险（每帧分配、忙等待循环、64 位假设），并附带函数证据；
- 一份以可玩的 index.html 为收尾的里程碑清单。
```

### 先移植逻辑核心（无头模式）

```text
使用 REA 提取 <game> 的纯模拟逻辑（物理、AI、规则）并与渲染与 OS 调用分离。用证据恢复精确规则，然后在 C/Rust 中实现逻辑核心并编译到 WASM，创建一个回放录制输入并比较状态哈希的测试用例。
```

## 7. 固件与嵌入式

### 固件镜像分流

```text
使用 REA 分析 <firmware image / bin / img>。

识别容器格式，提取分区/文件系统（JFFS2、SquashFS、UBI、cramfs 等），将每个区域映射到架构和加载地址，定位内核和 rootfs，并列出启动项、init 脚本和服务。

展示偏移量、熵观察与每个结论的证据。先进行静态分析，不要刷写或运行任何内容。
```

### MCU / IoT 二进制分析

```text
使用 REA 分析 <firmware blob>，目标为 <ARM Cortex-M / MIPS / AVR / ESP32>。

找到向量表和复位处理程序，从字面量池和外设基址恢复内存映射，基于符号/字符串指纹识别 RTOS（FreeRTOS、Zephyr 等），并映射主任务循环和外设驱动（UART、SPI、I2C、无线电栈）的函数地址。
```

### 嵌入式协议与更新机制

```text
使用 REA 分析 <firmware>，恢复：网络栈用法（硬编码 IP、DNS、MQTT/HTTP 端点、端口）、OTA 更新路径（下载 URL、签名检查、闪存写入）以及凭据材料（密钥、默认密码、调试令牌）。对每个发现都给出函数/地址，并说明该行为是已静态确认还是仍为假设。
```

## 8. Android

### 审计 APK

```text
使用 REA 分析 <PATH TO APK>。

列出声明权限、导出的组件、分析/追踪 SDK、发现的域名和本地存储机制。

对每项发现，展示对应类、方法或文件。

区分代码中出现的引用和实际被观察到的行为。不要仅因为字符串中出现某个域名就断定它一定被访问。
```

### 跟踪 Java/Kotlin 与原生代码中的功能

```text
使用 REA 对 <APK> 进行分析，端到端追踪 <FEATURE>：UI 入口点（Activity / Fragment / Composable）、Java/Kotlin 调用链、任何 JNI 边界（RegisterNatives / native library loads）、涉及的 .so 函数，以及最终效果（网络调用、文件写入、数据库行）。在每一步都展示类、方法和偏移量证据。
```

### 存储、加密和秘密审查

```text
使用 REA 分析 <APK>。确定应用如何存储 <data>：SharedPreferences、SQLite、文件、keystore。恢复嵌入式加密（硬编码密钥/IV、混淆算法）及其使用类/方法。说明数据是否在静态存储和传输中加密，并附带证据，随后列出具体风险。
```

### 混淆 / 打包应用分流

```text
使用 REA 分析 <APK>，若它看起来被混淆或打包。识别打包器或保护器（字符串/类指纹、原生库中的加载器桩），区分静态可见内容与运行时才推迟的部分，并给出安全到达真实 dex/原生代码所需的最小步骤。
```

## 9. 内核分析

### 驱动程序检查（Windows / Linux）

```text
使用 REA 分析 <driver binary: .sys / .ko>。

识别格式和目标 OS 版本、入口/初始化例程、设备对象和驱动分发表、每个 IOCTL 代码及其输入/输出缓冲区校验方式、注册的回调/通知，以及它在自身分配外读取或写入的内存。

将每一发现映射到函数/地址证据。仅进行静态分析，不要加载驱动。
```

### IOCTL 攻击面枚举

```text
使用 REA 分析 <driver>。枚举所有控制码及其处理方法：处理函数、输入/输出缓冲区如何校验（probe 方法、大小检查、IRQL 假设），以及任何带攻击者控制长度的 copy_to_user/copy_from_user 或 memcpy。基于证据给出处理器风险排序。
```

### 内核子系统 / 系统调用行为

```text
使用 REA 分析 <kernel binary or module>，解释 <subsystem/syscall> 如何处理 <input>。从系统调用/分发入口追踪到解析函数，展示边界检查（或缺失）、填充的数据结构和错误路径。对每一步附以地址证据。
```

## 10. 漏洞研究

### 信任边界审计

```text
使用 REA 审查 <authorized application or binary> 的安全性。

优先检查信任边界、不可信输入、特权操作、凭据存储、IPC、文件处理和命令执行。

对每个可能的漏洞，给出：
- 输入来源与敏感操作；
- 代码路径和现有检查；
- 前提条件和影响；
- 证据与不确定性；
- 受控验证建议。

在证据不足时，不要将假设直接归类为已确认漏洞。
```

### 从不可信输入发起“汇点搜索”

```text
使用 REA 分析 <binary>。列出所有不可信数据进入的地方（网络套接字、文件、IPC、命令行、剪贴板、URL 处理器），并跟踪它们到危险汇点：memcpy/strcpy 的未校验长度、system/exec、动态加载、反序列化、路径拼接。对每个 source→sink 路径，给出函数链与地址，并说明中间是否存在校验。
```

### 补丁比对（1 天到不完全修复的挖掘）

```text
使用 REA 比较 <vulnerable version> 和 <patched version> 中的 <component>。

对安全相关函数做差异分析：新增了什么检查、相同模式在修复之外的其他位置是否存在，以及该修复是否覆盖了所有该脆弱例程的调用者。报告候选的不完整修复位置，附带函数/地址证据，并明确标记为假设，直到在受控环境中验证。
```

### 崩溃排查到根因

```text
使用 REA 调查 <application> 中的崩溃。

可用证据：
<STACK TRACE, LOGS, DUMP OR REPRO STEPS>

将错误与相关函数对应起来，形成假设，并指出每个假设分别有哪些证据支持。

提出区分假设并验证根因所需的最小实验。
```

### 我的数据会如何处理？

```text
我允许分析 <program>。使用 REA 找出它存储或发送 <kind of data> 的位置，展示代码路径，说明数据是否在静态存储和传输中加密，并附带证据列出具体风险。
```

## 11. Electron 与 JavaScript

### Electron 应用结构解析

```text
使用 REA 分析 <PATH TO ELECTRON APP>。

定位 JavaScript 文件以及任何 app.asar 归档。绘制主进程和渲染进程地图、preload 脚本和 IPC 通道。

然后沿着 UI 到实现的路径追踪 <FEATURE>，包括网络调用和文件系统操作，并展示证据。
```

### IPC 与 contextIsolation 安全审查

```text
使用 REA 分析 <Electron app>。枚举每个 ipcMain 处理器，以及通过 contextBridge/preload 暴露的通道。对每个通道说明：它接受什么参数、是否会调用 shell.openExternal、child_process、fs 或 webview 导航，以及是否存在校验。标出任何从渲染器控制输入直接流向特权汇点而无检查的处理器，并附带文件和函数证据。
```

### 压缩 / 打包 JS 中的功能追踪

```text
使用 REA 分析 <app.asar / bundle.js>，追踪 <FEATURE> 是如何在压缩代码中工作的。
识别模块边界，恢复相关函数的可读名称，沿着从 UI 事件到网络/文件系统副作用的路径跟踪数据流，并生成调用图。对每一跳标注 bundle 中的偏移量。
```

## 12. 反作弊与保护研究

> 仅在你的机器、你的软件、供应商漏洞赏金、CTF 或学术研究场景中应用这些方法。不要在其他玩家的实时比赛会话中使用。

### 绘制反作弊检测面

```text
使用 REA 分析我实验室机器上的 <anti-cheat driver/service binary>。

识别：它枚举了哪些内容（进程、模块、句柄、回调）、执行了哪些完整性检查、挂钩或注册了哪些内核功能，以及它向外发送了哪些数据（端点、间隔、负载字段）。

对每个发现附上函数/地址证据。区分“代码存在”和“行为已观察”。先做静态分析，不要运行目标游戏。
```

### 测试我自己的产品保护机制

```text
我拥有 <my application> 及其保护方案。使用 REA 从攻击者视角评估它：定位许可证检查、完整性检查、反调试/反虚拟机技巧，并跟踪失败检查会触发什么。报告哪些检查很容易绕过、哪些是关键负载，以及具体修复方案——每个结论都要有文件/函数/地址证据。
```

### DRM / 许可证流分析（互操作性）

```text

```

## 13. DMA 与硬件辅助作弊研究（防御性）

> DMA 攻击是真实存在的反作弊和平台安全问题。使用这些方法可以研究检测机制并加强你自己的产品/实验室——前提是目标是你自己拥有的机器、离线目标或经过供应商授权。未经授权地通过 PCIe 读取其他机器内存，在大多数司法管辖区都是违法的。

### 目标平台上的 DMA 内存访问如何工作

```text
使用 REA 分析我实验室中的 <anti-cheat driver / DMA-protection firmware（例如 Thunderbolt 安全、IOMMU/VT-d 配置）>。

用函数/地址证据解释：平台如何限制外部 PCIe 内存读取（IOMMU 映射、Thunderbolt ACL、内核 DMA 保护）、反作弊会枚举什么以识别 DMA 设备（PCIe 拓扑、BAR 区域、未知根端口、时序异常），以及哪些检查是关键负载、哪些只是表象。
```

### 分析 DMA 作弊工具链样本（恶意软件风格）

```text
我拥有一个用于防御研究的样本 <DMA firmware / PCILeech-style driver / user-mode reader>。使用 REA 记录：它如何打开物理内存（XNVIPHYSTREE 风格访问、PCIe BAR 映射），如何定位游戏进程（PEB 遍历、页表遍历），读取/写入什么，以及任何反检测技巧（模式扫描规避、时序填充）。给出每个阶段的函数链和地址。不要对任何实时游戏运行它——仅用于分析。
```

### 评估我自己的产品存在的检测缺口

```text
使用 REA 评估 <my application/my anti-cheat component> 对外部物理内存访问的反应：有哪些完整性检查、敏感值是否落在可预测的内存位置、服务器执行了哪些侧信道校验。提出具体加固措施（值混淆、服务器端校验、内存布局随机化），并映射到需要修改的代码位置。
```

### FPGA / 微控制器设备固件研究

```text

```

## 提示词编写技巧（为什么这些方法有效）

1. **每条提示词只关注一个功能。** 宽泛的“解释整个应用”问题只能得到浅层地图；更窄的问题才能返回调用链和地址。
2. **要求证据。** 这里的每个提示词都要求文件/函数/地址引用——这能阻止代理编造信息。
3. **区分事实 / 推断 / 未知。** 三桶法能让假设保持诚实。
4. **静态优先。** 先说“不执行应用程序”，直到确实需要运行时观察。
5. **以可交付成果结尾。** SPEC.md、读取器脚本、端口计划、最小重建——具体产物能迫使代理自检。
6. **明确说明范围。** “我自己的实验室机器”“离线单人”“只做文档，不绕过”——这样能保持结果可用且可报告。
